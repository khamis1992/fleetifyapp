# تصميم معالجة تدقيق الوكلاء — 2026-08-27

## النتيجة المستهدفة

منظومة وكلاء آمنة ومتعددة الشركات، قابلة للإيقاف والإلغاء، تمنع تكرار التنفيذ، وتحول نتائج المراجعة والتدخل البشري إلى مهام كاملة يمكن تتبعها دون الاعتماد على فتح لوحة التحكم في المتصفح.

## الخيارات

### 1. ترقيع مباشر لكل مشكلة

سريع في البداية، لكنه يُبقي مزامنة المتصفح وتداخل المجدولات وتعدد مسارات التحكم. غير معتمد.

### 2. إعادة بناء شاملة لمنظومة الوكلاء

أنظف نظرياً، لكن مخاطرتها عالية على إنتاج نشط ويصعب التحقق منها دفعة واحدة. غير معتمد.

### 3. معالجة مرحلية حول Control Plane موحد — المعتمد

نحتفظ بالجداول والعامل الحاليين، ونضيف طبقة تحكم صغيرة وخدمات مزامنة idempotent، ثم ننقل المسارات واحداً تلو الآخر مع قياس النتائج وإمكانية الرجوع.

## التصميم

### حدود الأمان

- الجداول التشغيلية متعددة الشركات: RLS إجبارية بسياسات `company_id` وصلاحيات أقل حد ممكن.
- جداول audit/backup/staging: لا تُتاح للعميل؛ تُسحب grants من `anon` و`authenticated`، وتُترك للخدمة/الإدارة فقط. لا تُنشأ سياسة عامة لمجرد إسكات المستشار.
- استدعاءات cron تقرأ عنوان المشروع وبيانات المصادقة من Vault، ولا تضمّن token داخل SQL.
- RPCs الحساسة تكون ذات `search_path` ثابت، وتتحقق من دور المستخدم والشركة، ولا تعتمد مدخل `company_id` وحده.

### طبقة التحكم

جدول تحكم واحد لكل شركة/نوع وكيل يحفظ: `enabled`, `paused_at`, `paused_by`, `pause_reason`, `kill_switch`, ونسخة optimistic-lock. وتضاف RPCs مخولة لتغيير الحالة وطلب إلغاء run. يحفظ `initiated_by` و`requested_by` لكل تشغيل يدوي.

العامل يفحص التحكم قبل claim، ثم يفحص `cancel_requested_at` وحالة الإيقاف بين الدفعات. الإلغاء تعاوني وآمن: لا يقطع معاملة جارية، لكنه يمنع claim/كتابة جديدة بعد نقطة الفحص.

### مزامنة المراجعات

تنتقل من hook المتصفح إلى خدمة خادمية. يُنشأ mapping فريد بين المفتاح المنطقي للـfinding ومهمة المستخدم. تتم المزامنة تحت advisory lock وعلى دفعات، باستخدام upsert، ثم تؤرشف الروابط التي غابت فقط عندما تكون snapshot مكتملة. بذلك تصبح إعادة التشغيل آمنة ولا تعتمد زيارة المستخدم للوحة.

### منع التداخل

كل وكيل mutating يعلن resource key واضحاً. قبل التنفيذ يأخذ قفلاً استشارياً أو lease محدوداً. تُشغّل النسخة الجديدة أولاً بوضع shadow/read-only، وتُقارن النتائج، ثم يُعطّل المجدول القديم القابل للاسترجاع. لا تُحذف وظائف Edge القديمة حتى مرور فترة مراقبة ناجحة.

### تقاضي والتنبيهات

تُحوَّل حالات `needs_human` إلى مهام بمفتاح فريد يرتبط بالـjob والسبب، مع مالك/مهلة وحالة رجوع. تُرسل التنبيهات عبر البنية الحالية بعد فحصها، عند: فشل run، backlog فوق الحد، عدم تشغيل cron في نافذته، أو بقاء تدخل بشري بلا معالجة.

### البريد المروري

لا يُنشر `ingest-traffic-mail` لمجرد وجود الكود المحلي. يُفحص auth وcompany isolation وidempotency وGraph configuration، ثم dry-run على صندوق محدد، وبعدها جدولة Vault-backed مع مراقبة checkpoint.

## الترحيل والرجوع

- كل migration لها rollback مطابق في `supabase/rollbacks`.
- إضافة الجداول/الأعمدة قبل تحويل القراءات والكتابات.
- تشغيل backfill على دفعات مع عدادات قبل/بعد.
- تعطيل المسار القديم بعد التحقق فقط؛ الرجوع يعيد تفعيله ولا يحذف البيانات الجديدة.
- تدوير أي سر ظهر داخل cron بعد تحويل الاستدعاءات؛ القيم نفسها لا تُسجل في Git.

## التحقق

- اختبارات SQL لصلاحيات anon/authenticated/service-role وعزل شركتين.
- اختبارات تزامن لإعادة المزامنة والإلغاء بين الدفعات ومنع تشغيلين mutating متوازيين.
- مقارنة latest findings مع task mappings، ويجب أن تكون الفجوة صفراً بعد المزامنة.
- فحص cron definitions للتأكد من غياب JWT الخام.
- `npm run type-check`, الاختبارات المستهدفة، `npm run build:ci`، ثم مراجعة كود وأمن مستقلة قبل الإنتاج.
